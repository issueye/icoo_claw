# 动态页面系统需求文档

日期：2026-05-19  
项目：d_page  
技术栈：Vite library mode + Vue 3 + JavaScript + Tailwind CSS + Pinia

## 1. 背景与目标

本项目需要开发一个“通过 JSON 配置直接渲染页面”的动态页面系统。系统的核心目标是把页面结构、组件类型、样式、数据绑定、交互行为和状态管理尽量配置化，使业务页面可以通过维护 JSON 完成搭建和调整，减少重复编码成本。

当前实施形态调整为 npm 组件包，而不是优先建设独立业务应用。`d_page` 应先沉淀为可发布、可版本化、可被宿主 Vue 应用消费的动态页面渲染包，包名建议为 `@icoo-claw/d-page`。成熟后，`desktop/frontend` 的 chat 消息渲染可以按 metadata 选择接入该包，用于展示动态卡片、表单、工具结果和交互页面片段。

该系统不定位为完整低代码平台的全功能编辑器，而是优先建设一个可运行、可扩展、可维护的 JSON 驱动页面渲染内核。后续可以在此基础上扩展可视化编辑器、远程 schema 管理、权限控制、表单提交、数据源编排等能力。

包化改造方案见：`docs/plans/2026-05-19-npm-component-package-plan.md`。

## 2. 产品定位

动态页面系统面向以下场景：

- 后台管理页面快速搭建，例如列表、详情、表单、统计看板、配置页。
- 运营活动页或信息展示页，通过 JSON 调整布局、文案、图片和按钮行为。
- 内部工具页面复用，统一组件规范和交互模型。
- 需要频繁调整页面但不希望频繁发版的业务模块。

系统第一阶段重点解决“JSON 到页面”的可靠渲染问题，暂不优先建设拖拽式可视化搭建器。第一阶段输出物应是 npm 包和可运行示例，而不是只能在 `d_page` 内部运行的单页应用。

## 3. 目标用户

### 3.1 页面配置者

通常是前端开发、实施人员或具备基础技术能力的产品/运营人员。主要关注：

- JSON 配置是否容易理解。
- 页面修改是否无需改 Vue 代码。
- 出错时是否能快速定位问题。

### 3.2 系统开发者

负责维护渲染引擎、组件注册、数据源、动作系统和状态管理。主要关注：

- 架构是否清晰。
- 组件和动作是否容易扩展。
- 配置错误是否可控。
- 后续是否能接入远程配置和权限体系。

### 3.3 最终访问用户

实际使用动态页面的人。主要关注：

- 页面加载速度。
- 交互是否稳定。
- 表单、按钮、列表、弹窗等功能是否符合常规使用习惯。

## 4. 范围说明

### 4.1 本期范围

- 使用 Vite library mode 创建 Vue 3 组件包。
- 使用 JavaScript 作为开发语言。
- 使用 Tailwind CSS 作为主要样式方案。
- 使用 Pinia 管理全局页面状态、运行时上下文和组件状态。
- 设计并实现 JSON 页面协议。
- 根据 JSON 渲染页面布局、基础组件和嵌套组件。
- 支持基础事件动作，例如跳转、弹窗、状态更新、接口请求、表单提交。
- 支持本地 JSON 示例配置加载和包内 examples。
- 支持组件注册机制，方便后续扩展组件。
- 支持基础错误提示和配置校验。
- 提供稳定包入口，例如 `DPageRenderer`、`createDPageRuntime`、组件注册表和动作注册表。
- 以 `peerDependencies` 方式依赖 `vue`、`pinia`，避免宿主应用打包两份 Vue 运行时。

### 4.2 暂不纳入本期范围

- 拖拽式页面编辑器。
- 多人协同编辑。
- 完整权限后台。
- 可视化数据源编排器。
- 复杂工作流引擎。
- 服务端渲染 SSR。
- TypeScript 重构。当前明确使用 JavaScript。
- 面向公网生产环境的完整安全沙箱。
- 默认接入 chat 主消息流。chat 接入必须等包 API 和错误边界稳定后，通过 feature flag 或 metadata 分支逐步启用。

## 5. 核心用户故事

1. 作为页面配置者，我希望通过一个 JSON 文件描述页面结构，这样不用修改 Vue 代码也能调整页面。
2. 作为页面配置者，我希望可以配置标题、文本、图片、按钮、表单、列表、卡片、弹窗等常用组件。
3. 作为页面配置者，我希望按钮点击后可以触发跳转、请求接口、打开弹窗、更新状态等动作。
4. 作为系统开发者，我希望新增一个业务组件时，只需要注册组件和声明 props 映射，而不需要修改渲染器主流程。
5. 作为系统开发者，我希望 JSON 配置错误时页面能显示明确错误，而不是白屏。
6. 作为最终访问用户，我希望页面表现接近普通手写页面，交互稳定且加载速度可接受。

## 6. 功能需求

### 6.1 JSON 页面协议

系统需要定义统一的页面配置结构。建议顶层结构包括：

- `page`：页面基础信息，例如标题、描述、布局模式。
- `data`：页面初始数据或静态数据。
- `state`：页面运行时状态默认值。
- `actions`：可复用动作定义。
- `components`：页面组件树。
- `metadata`：版本、作者、更新时间等非渲染信息。

示例结构：

```json
{
  "page": {
    "title": "用户管理",
    "layout": "default"
  },
  "state": {
    "keyword": "",
    "dialogVisible": false
  },
  "actions": {
    "openCreateDialog": {
      "type": "setState",
      "payload": {
        "dialogVisible": true
      }
    }
  },
  "components": [
    {
      "type": "container",
      "props": {
        "class": "p-6 space-y-4"
      },
      "children": [
        {
          "type": "heading",
          "props": {
            "text": "用户管理",
            "level": 1
          }
        },
        {
          "type": "button",
          "props": {
            "text": "新增用户",
            "variant": "primary"
          },
          "events": {
            "click": "openCreateDialog"
          }
        }
      ]
    }
  ]
}
```

### 6.2 动态渲染器

系统需要提供一个核心渲染器，根据组件树递归渲染 Vue 组件。

渲染器需要支持：

- 根据 `type` 匹配组件注册表。
- 向组件传递 `props`。
- 渲染 `children` 嵌套结构。
- 绑定 `events` 中声明的交互动作。
- 在未知组件类型时显示降级错误组件。
- 在组件渲染异常时隔离错误，避免整个页面白屏。

### 6.3 组件体系

本期建议内置以下基础组件：

- 布局类：`container`、`grid`、`flex`、`section`。
- 展示类：`heading`、`text`、`image`、`card`、`divider`、`tag`。
- 操作类：`button`、`link`。
- 表单类：`form`、`input`、`textarea`、`select`、`checkbox`、`radio`、`switch`。
- 数据类：`table`、`list`、`stat`。
- 反馈类：`modal`、`drawer`、`alert`、`toast`。

组件设计原则：

- 每个组件只负责自己的展示和基础交互。
- 跨组件状态由 Pinia 管理。
- 复杂业务逻辑通过动作系统处理。
- Tailwind 类名可以通过配置传入，但需要保留默认样式，避免空配置时页面不可用。

### 6.4 状态管理

使用 Pinia 建立页面运行时 store，建议包含：

- 当前页面 schema。
- 页面级 state。
- 接口请求状态。
- 表单数据。
- 弹窗、抽屉、提示等 UI 状态。
- 动作执行上下文。

状态读取建议支持表达式引用，例如：

```json
{
  "props": {
    "text": "{{ state.username }}"
  }
}
```

本期表达式能力建议保持克制，优先支持简单路径读取，不引入任意 JavaScript 执行，降低安全和调试成本。

### 6.5 动作系统

动作系统负责处理用户交互。建议第一阶段支持以下动作类型：

- `setState`：更新页面状态。
- `navigate`：页面跳转。
- `request`：发起接口请求。
- `submitForm`：提交表单。
- `openModal` / `closeModal`：控制弹窗。
- `showToast`：显示提示。
- `chain`：按顺序执行多个动作。
- `condition`：根据状态或接口结果执行不同动作。

动作执行需要具备：

- 执行前参数解析。
- 执行中 loading 状态。
- 成功和失败回调。
- 错误提示。
- 防重复点击能力。

### 6.6 数据源与接口请求

本期建议先支持简单 HTTP 请求配置：

```json
{
  "type": "request",
  "payload": {
    "url": "/api/users",
    "method": "GET",
    "params": {
      "keyword": "{{ state.keyword }}"
    },
    "saveTo": "users"
  }
}
```

数据源能力要求：

- 支持 GET、POST 等常见方法。
- 支持 query、body、headers 配置。
- 支持请求结果写入页面 state。
- 支持 loading 和 error 状态。
- 支持 mock 数据，便于前端独立开发。

### 6.7 表单能力

表单组件需要支持：

- 表单字段配置化。
- 默认值。
- 基础校验，例如必填、长度、格式。
- 表单数据写入 Pinia store。
- 提交动作绑定。
- 重置表单。

本期表单校验可以先实现常见规则，不需要引入复杂动态规则引擎。

### 6.8 样式与主题

使用 Tailwind CSS 提供样式能力。

需求包括：

- 组件具备默认样式。
- JSON 可通过 `class` 或 `className` 扩展 Tailwind 类。
- 支持页面级主题变量，例如主色、圆角、间距密度。
- 需要避免完全依赖配置者手写 Tailwind，否则配置成本过高。

建议采用“默认组件风格 + 局部 Tailwind 覆盖”的方式。

### 6.9 配置校验与错误处理

系统需要对 JSON 配置进行基础校验。

校验内容包括：

- 顶层字段是否合法。
- 组件 `type` 是否存在。
- `props` 类型是否合理。
- `children` 是否为数组。
- `events` 引用的 action 是否存在。
- 动作 payload 是否满足最低要求。

错误处理要求：

- schema 加载失败时显示页面级错误。
- 单个组件错误时显示组件级错误占位。
- 动作执行失败时显示可理解的错误提示。
- 开发环境输出详细错误，生产环境输出简洁错误。

## 7. 非功能需求

### 7.1 可扩展性

组件、动作和数据源都应通过注册机制扩展，避免在核心渲染器中持续堆叠条件判断。

### 7.2 可维护性

目录结构需要清晰区分：

- 页面渲染器。
- 组件库。
- schema 解析。
- 动作执行器。
- Pinia store。
- 示例 JSON。
- 工具函数。

### 7.3 性能

本期性能目标：

- 普通页面配置渲染不应有明显卡顿。
- 大型组件树需要避免无意义的全量响应式更新。
- 列表和表格后续可扩展虚拟滚动。

### 7.4 安全

由于页面由 JSON 驱动，需要避免配置直接执行任意 JavaScript。表达式解析应限制为安全的路径读取、简单比较和白名单函数。

### 7.5 兼容性

优先支持现代浏览器，不要求兼容 IE。

## 8. 建议系统架构

建议采用以下模块划分：

```text
src/
  components/
    dynamic/
      DynamicRenderer.vue
      UnknownComponent.vue
      RenderError.vue
    base/
      DButton.vue
      DInput.vue
      DCard.vue
      DTable.vue
  registry/
    componentRegistry.js
    actionRegistry.js
  stores/
    pageStore.js
  schema/
    validateSchema.js
    resolveBinding.js
  actions/
    setState.js
    request.js
    navigate.js
    modal.js
  examples/
    user-management.json
  views/
    DynamicPageView.vue
```

架构原则：

- `DynamicRenderer` 只负责渲染组件树。
- `componentRegistry` 负责组件类型映射。
- `actionRegistry` 负责动作类型映射。
- `pageStore` 保存 schema、state 和运行时状态。
- `resolveBinding` 负责解析 `{{ }}` 绑定表达式。
- 业务组件不直接依赖 JSON 原始结构，只接收解析后的 props。

## 9. MVP 版本建议

第一阶段建议优先完成以下能力：

1. 项目初始化：Vite library mode + Vue 3 + JavaScript + Tailwind CSS + Pinia。
2. JSON schema 基础格式。
3. 递归动态渲染器。
4. 组件注册表。
5. 基础组件：container、heading、text、button、input、card、modal。
6. Pinia 页面状态 store。
7. 简单绑定表达式：读取 state 和 data。
8. 动作系统：setState、showToast、openModal、closeModal、chain。
9. 示例页面：一个包含标题、输入框、按钮、卡片、弹窗的页面。
10. 基础错误组件和 schema 校验。
11. npm 包入口、构建产物和 peer dependency 配置。
12. 面向 chat 的示例 schema，例如工具结果卡片、确认表单、表格摘要。

MVP 暂不建议一开始就做复杂表格、复杂表单规则和远程页面管理，否则容易导致渲染内核还未稳定就过早复杂化。

## 10. 验收标准

### 10.1 页面渲染验收

- 给定合法 JSON，系统可以正确渲染页面。
- 支持组件嵌套。
- 未知组件不会导致页面白屏。
- JSON 修改后页面表现随配置变化。

### 10.2 状态与交互验收

- 按钮点击可以触发配置的动作。
- `setState` 后绑定到状态的组件能自动更新。
- 弹窗可以通过 JSON 动作打开和关闭。
- 动作执行失败时有错误提示。

### 10.3 开发扩展验收

- 新增一个组件时，只需要新增组件文件并注册映射。
- 新增一个动作时，只需要新增动作处理函数并注册映射。
- 示例 JSON 能覆盖主要用法。

### 10.4 工程验收

- 包可以本地启动 demo 或 preview。
- 构建命令可以通过。
- 构建产物可以被外部 Vue 应用 import。
- 代码结构清晰。
- 关键逻辑有必要的单元测试或手动验证说明。

## 11. 关键风险与约束

### 11.1 JSON 协议过度复杂

如果一开始试图覆盖所有页面类型，协议会迅速复杂化。建议先围绕 MVP 建立稳定协议，再逐步扩展。

### 11.2 表达式能力带来的安全风险

不建议支持任意 JavaScript 表达式。应优先支持白名单能力，例如路径读取、简单条件、少量格式化函数。

### 11.3 样式配置失控

如果所有样式都依赖 JSON 中手写 Tailwind 类，页面一致性会变差。基础组件应内置默认视觉规范。

### 11.4 组件抽象边界不清

动态页面系统容易把所有逻辑塞进渲染器。应确保渲染器、组件、动作、状态、数据源各自职责清晰。

## 12. 后续迭代方向

- 远程加载页面 JSON。
- 页面 schema 版本管理。
- 可视化 schema 编辑器。
- 更完整的表单组件和校验系统。
- 表格查询、分页、排序、筛选配置。
- 数据源预加载和依赖编排。
- 权限控制和组件级显隐规则。
- 国际化。
- 主题系统。
- 页面导入导出。
- 配置变更预览和发布流程。

## 13. 待确认问题

1. 页面主要面向后台管理系统，还是也需要支持营销活动页？
2. JSON 配置来源是本地文件、后端接口，还是未来会有配置平台？
3. 是否需要在第一阶段支持真实接口请求，还是先以 mock 数据为主？
4. 是否需要支持路由级动态页面，例如 `/page/:id` 根据 id 加载不同 JSON？
5. 是否有既定 UI 风格或组件规范需要遵守？
6. 是否需要兼容移动端布局？

## 14. 推荐结论

建议第一阶段按“MVP 动态渲染内核”推进：先完成 JSON 协议、组件注册、递归渲染、Pinia 状态、基础动作和示例页面。这样可以尽快验证系统核心价值，并为后续扩展表单、表格、远程配置和可视化编辑器打下稳定基础。

## 15. 渲染标准补充

系统渲染协议进一步明确为“卡片树渲染”：以卡片作为最小动态渲染单元，页面本身也是一种特殊卡片。表单、表格、图表、自定义业务组件等能力都应挂载在卡片内部，并通过组件注册机制动态扩展。

详细标准见：`docs/standards/2026-05-19-card-rendering-standard.md`。
